# Experience design

Pyre should be a pleasant place to see and direct work, while keeping the agent terminal immediately accessible. The initial UX described here is a design brief, not a pixel-perfect specification. Build an interactive prototype against the fake backend early and refine it using the scenarios in the product spec.

## Terminal overview

Three primary destinations: **Sessions**, **Projects**, and **Inbox**. In the terminal the first two are tabs; the inbox is the web app (`pyre web serve`), and the TUI header shows `● N asks` linking to it (see "Inbox and notifications"). Machines, accounts, connections, environments, and updates are available through the command palette and management views. Do not put all management tables on the home screen.

An illustrative layout:

```text
 Pyre          Sessions  Projects  ● 3 asks                  / Search

 Sessions                       Current selection
 ● outfit API       server         Claude · working · updated 2s ago
 ? release review   mac         Project: Outfit · branch api-client
 ○ research         server         Account: personal-2 · health current
 ◌ scratch          laptop      Latest activity and terminal preview

 Needs you: review proposal      [Enter] Join  [m] Message  [p] Project
                                [:] Commands  [?] Help
```

This is illustrative. A polished implementation needs responsive sizing, restrained color, readable density, stable selection during updates, and visible keyboard hints. Status cannot rely on color alone. Search and the command palette should be usable with a narrow terminal and without a mouse.

### Session row

Show a useful name, harness, machine, current activity, last update, and an attention indicator. Project and account are available without making every row too wide. Distinguish working, waiting for input, idle, offline/stale, and failed. Unknown runtime state is a valid state.

Enter attaches to the real session through its verified adapter; detach returns to the same list/filter/selection. The UI itself does not own the agent lifetime. A session list should remain usable when a node is slow or offline.

### Launch flow

Choose a machine and Claude, Codex, or a supported shell. Choose a directory or optionally a project. Resolve defaults for account and environment, show the selected values, and launch. Project-specific worktree creation is available, not compulsory. A saved launch preference makes the common case short.

Natural-language orchestration uses the same launch operations. It must not need a separate wizard or a different definition of a session.

A session started by another session reports back to it without depending on prompt wording (W-childnotify). The hub sends the starting session an ordinary Pyre message from the child (queue mode, so the parent's doorbell and `[pyre-msg:…]` delivery apply, and a reply threads back to the child) when the child:

- ends a turn and waits for input. The message carries the child's last assistant message (at most 1500 characters), title, machine and state. There is one report per turn, and none when the child itself messaged the parent in the five minutes before that turn ended (it sent its result, then went idle); a question or coordination message earlier in a long turn does not count;
- needs input (an approval or question). The message lists pending approval IDs so the parent can use `answer_approval`, or else tells the owner;
- exits or fails. The message gives the reason and exit code. A launch that never ran (for example no account with capacity) reads "<title> could not start: no Codex account with capacity right now; it can resume after the reset" and says the owner was not told. A failure reaches the parent even when the child opted out of reports, since it no longer reaches the owner.

Reports wait while the parent is mid-turn: when its turn ends (or after 20 minutes) everything ready for it goes out as one digest message ("3 reports from sessions you started: …", one numbered part per child, each naming the session to `send_message`); a lone report still comes from its child. A child that exits cleanly after its last message already reached the parent (its idle report, or its own message in the five minutes before its turn ended) wakes nobody: "Also exited cleanly since: …" rides along with the parent's next report. A child that ends its turn while its own CI run, review or watcher is still pending calls `waiting_on` (`pyre waiting-on "<job> <url>" --expect 30`) first; the parent then gets "<title> is waiting on its own job: <job>" (not idle, don't give it new work) and, if no new turn started by the expected time, "<title> may be stuck". With `quiet` (`--quiet`) the parent gets nothing for that turn, only "may be stuck" (with the child's last message) if the child is not woken in time, and the exit report as usual: a child lead waiting on its own workers ends its turn instead of polling its inbox. A top-level session that does this is not flagged as waiting on the owner.

Every session started in a project gets the project's fact sheet in its launch context: a document (slug `facts`) of settled facts, each with the owner's words, proposed by a session with `propose_fact` (`pyre propose fact "<fact>" --why "…"`) and added only when the owner approves that ask, quoting his answer (or marked "owner approved proposal" when he typed nothing); shown with `pyre fact ls`. The standing grants that hold for the new session are listed under it.

Nothing is sent to an archived parent or a parent without a live run, and the owner's inbox is never used as a fallback. An archived child still reports: a child that archives itself at the end of its last turn (the normal finish of a bounded task) gets one report, "<title> finished and archived itself: <first sentence>", with its last message, and a child the owner or Pyre archived is reported as archived unless its turn had already been reported (archiving many idle children at once sends nothing new). A parent that archives its child after a turn ended gets nothing more about that turn, since it already knows; one that schedules the archive mid-turn still gets that turn's result. Reports per child are rate-limited (12 per 10 minutes) so a parent and child that keep answering each other cannot loop. This is on by default when a session starts the child (`start_session report_to_parent`, `pyre start --no-report` to opt out). Owner-started sessions are unaffected. The choice is the reserved tag `report:parent` / `report:none` on the child, and editing the tags toggles it. The child's guide and environment (`$PYRE_PARENT_SESSION_ID`, `$PYRE_REPORT_TO_PARENT=1`) say who started it and that its turn summary is relayed. It need not message the parent unless asked, and it messages the owner only when told to. The TUI session facts and the Android session details show "Started by <parent title>", followed by "· reports to parent" when reports are on.

Finished work is cleaned up without being asked. A child session (started by another session) whose run exits with a recorded exit code of 0 is archived about five minutes after its final report reaches the parent; the report says so. A failed child, or one whose run ended without an exit code (reboot, out-of-memory kill, pyred restart), stays for the parent to look at, and so does a child Pyre is moving to another account. Whenever Pyre archives a session by itself (that case, a session archived when done, the nightly sweep), the session's machine stops the processes it left running in its own terminal session (background shells and watchers; servers that detached, like the tmux server, adb or gradle daemons, are left alone) and removes the git worktrees Pyre created for that session at launch (their marker names it), but only those with no uncommitted changes and no ignored files other than rebuildable ones (node_modules, .venv, build output), not on the default branch, whose branch is merged or contained in its own upstream, and that no live session or process works in. Worktrees you or an agent made by hand are never removed automatically. Once a night (between 03:30 and 05:00 in the owner's time zone) the hub archives sessions that failed to launch or ended over a day ago, each machine removes orphan Pyre-created worktrees of finished sessions under the same rules (untouched for a day) and Claude temp folders of sessions untouched for three days, and the owner gets one "Nightly cleanup" message: what was archived, removed and kept, and why. Until one such report has reached the owner, every sweep is a dry run that only reports what it would do. Archived sessions keep their history and can be resumed or unarchived.

Placement (W6). A launch that names no machine (`pyre start` or `start_session` without `--node`/`node`) goes to the least loaded eligible node, not automatically the caller's. A node is eligible when it is connected, has the harness available, is below its advertised run capacity and can run the launch's account. That last check uses each node's dry-run `account.select`: an explicit `--account` must be the account selected there, `--ambient` needs the node's own login, and otherwise the node needs an eligible account now or its own login. A node that cannot answer the dry run is not excluded. Windows nodes are left out unless the caller runs on Windows or no other node is eligible. With `--project --repo`, only nodes holding a recorded checkout of that repo count. `--cwd` is a path on the caller's machine, so it stays there. With neither `--cwd` nor a repo, the session starts in the chosen node's home folder (`~`). Load comes from each node's last heartbeat: CPU, memory in use, swap in use, memory pressure and live runs. A node with under 2 GB free is penalised, and a node that reports no machine stats ranks as moderately busy. Runs still starting there (from the hub) and launches this process placed in the last two minutes count as load, so a burst of starts spreads out. The caller's own machine wins near-ties. `pyre new <repo>` picks the least loaded of the machines that hold the repositories, and recency only breaks ties. The CLI prints `placed on <node>: <why>` on stderr, and MCP returns `placement` {node_id, node_name, reason} beside the session.

Monitors (W6). `pyre monitor add --every 10m --cmd '<shell check>' [--session S] [--node N] [--until-change] [--for 24h] [--initial]` watches external state without agent turns. It starts a shell session (tagged `monitor` and `monitor-to:<session>`, title `monitor: <label>`) that runs `pyre monitor run`. Every interval (minimum 1 minute) it runs the command with `sh -c` (PowerShell on Windows). The command runs in its own process group (a process tree on Windows). A check that outlives its interval (at most 10 minutes) is killed with all its children, and at most 1 MB of its output is kept. It compares the combined output plus any nonzero exit status with the previous check. Only on a change does it send the target session an ordinary Pyre message as the monitor session, quoting the new output (last 3000 bytes) and the previous one. The first check is the baseline (`--initial` reports it too). A failed send is retried on the next check. While the target is mid-turn (running or starting), changes are held and only the latest is sent once it is idle. At most 6 wakes are sent per rolling hour; a 7th change sends a final notice and stops the monitor, because a check that noisy is a bad monitor. The monitor ends when its target is archived or deleted. `--until-change` ends after the first delivered change. `--for` ends after a duration (default 7 days). Each check is one line on the monitor's screen (`pyre read <monitor>`). `pyre monitor ls` lists monitors and `pyre monitor rm <monitor>` stops and archives one. A monitor keeps running after the session that created it ends. Monitors are plumbing, not work: session lists (`pyre sessions`, MCP `list_sessions`, the TUI, the web app and Android, which all use `sessions.list`) leave them out, and they never count toward "needs you", idle reports or project counts. The session a monitor wakes shows a "watching N" badge instead (TUI row and facts, web session rows, `pyre sessions` state column, `pyre sessions show`, MCP lines); `pyre sessions --monitors` (MCP `include_monitors`) lists them, and `pyre read`/`pyre sessions show <monitor>` work as before. A monitor is identified by its `monitor` tag only (a shell titled `monitor: …` without it is an ordinary session); the badge counts monitors whose run is starting, running or waiting (not unknown, when the node lost contact, nor ended). A hub request for `harness: shell` alone still includes monitors, so older CLIs' `pyre monitor ls/rm` keep working; `pyre prune` archives ended monitors too. A repeat of the same `pyre monitor add` (same command, machine, directory, `--every`, `--for`, `--until-change` and `--initial`, same target and caller) returns the caller's live (starting, running or waiting) monitor instead of starting another (`reused` in `--json`). Claude Code has its own wake (its Monitor tool, Bash `run_in_background` notifications), so the agent guide steers Claude sessions to it for short waits and keeps `pyre monitor` for waits that must outlive the Claude process and for Codex and agy; `pyre monitor add` run from Claude Code prints a one-line hint and proceeds. pyred sets `$PYRE_HARNESS` in every run; `pyre mcp`, `pyre guide` and the hint use it (outside a Pyre session, `CLAUDECODE=1`).

### Interaction and takeover

Messages enter the harness's supported queue or input mechanism. If a harness requires an explicit local/remote ownership switch, the UI says so and preserves the native session. Do not imply that all harnesses support concurrent typing, live steering, and every approval type.

Display queued messages and allow supported cancellation. An uncertain delivery stays visible with a reconciliation action; a retry button must not silently duplicate an unknown execution. Manual terminal input and remote approvals must reconcile against the same runtime state.

## Project home

The home should answer: what are we trying to accomplish, what changed, where is the current work, and what needs review?

- **Overview:** a short brief, useful links, current sessions, and recent activity.
- **Docs:** searchable versioned text, readable in the UI and editable through a normal editor workflow.
- **Artifacts:** previews/downloads, versions, producer/session provenance, and review comments.
- **Discussion:** project threads with links to sessions, documents, and outputs.
- **Work:** optional checklist/assignments/dependencies for projects that benefit from them.

The home must work for a project with no Git repository. Linking multiple repos should be normal. Native work directories remain on their nodes; the shared document and artifact area has its own durable published state.

### Documents

Open a document in the terminal reader, Android reader, or local editor. Editing starts from a known revision. Saving/publishing creates a version; if another writer has changed it, preserve the draft and show a conflict rather than losing either edit. A pending local draft and a published version are clearly different.

Agents use the same read/publish operations. A concise project brief can be supplied at session start; additional documentation is retrieved as needed rather than dumped into every prompt.

### Artifacts and review

Publish a file or result link with a title and optional description. A local path is not sufficient to make it shared. A successful publish receipt means bytes and metadata are retrievable independently of the producing node.

Support Markdown/text, images, PDFs, HTML previews, and downloadable arbitrary files. Use existing viewers and platform open/share behavior. Do not implement an office suite. HTML renders in an isolated viewer that cannot access hub credentials or administration APIs.

Comments attach to an exact artifact/document revision and can mention a session. The notification links back to the relevant review. A follow-up version preserves previous comments and makes the revision relationship visible. Mobile should make it easy to say “this part needs changing” and send that feedback to a worker.

## Inbox and notifications

The inbox gathers user-directed questions, approvals, failures, exhausted account pools, completed results needing review, and important messages. Collapse repeated events into one ongoing incident with updates. Allow quiet hours, per-project muting, and filtering.

Failures stay small too (owner report 2026-10-12: 84 stale "Session run failed" items, a Sessions badge of 44 with no live session needing the owner, decision I32):

- A failed run of a session started by another session goes to that parent (its child report), never to the owner's inbox.
- Owner-started launches that failed only because no account of a provider had capacity are one item per provider: "Codex out of capacity: 12 launches waiting for the reset", with the sessions listed. It shrinks as those sessions are archived or run again and goes away with the last one.
- Every other owner-started failure is one item per project and cause (owner report 2026-10-17: 332 "Session run failed" items in two weeks, 179 on one day): "12 sessions failed to start: working folder missing", "5 sessions crashed: exit code 1", with the sessions listed and what to do. The cause leaves out per-session detail (IDs, paths, numbers, times); a reason Pyre does not recognise still groups with identical ones but is never copied ("3 sessions failed to start"). One failure reads "'<title>' failed to start: <cause>" with its full reason. The phone is notified once per item, not per session that joins it; a session that fails again for another cause moves to that item. Each member session keeps its own failure flag.
- A failure item resolves itself when its session is archived or a later run of it goes live (a retry that only starts and fails again keeps the one item). An "account limit" item resolves when its session ends or is archived; one raised after the session stopped (waiting for the reset) stays. Hub maintenance sweeps items the events missed.
- A session whose current run failed at launch is never "needs you": its failure flags it at the message level only. A session that crashed after it ran still is.
- The Sessions badge, the "Needs you" strip, project summaries and the digest count a session only when it is not archived and either waits on an approval or has a blocking item the owner can act on; a failure or account-limit reason counts only while the session's run is live. Ended failures still show in their row ("✗ failed", "⊘ re-auth") and in the inbox.
- The Android Inbox opens on **All** (asks first, under "Decisions"), and its badge is the number of rows that list shows (read rows included; done and snoozed excluded).
- A message item's detail shows the newest message in full and earlier ones in its thread as one-line excerpts, from the owner's already-listed mail (never a per-message fetch, which would count as reading it).
- The terminal UI has no inbox view or side panel (owner request 2026-10-15); the inbox is the web app (`https://pyre-example.ngrok.app` by default; `web_url` in the client config or `PYRE_WEB_URL`). The TUI header shows `● N asks` (red when one is urgent or due within 15 minutes), lead chips `● asks N` and project headers `● N asks`, each a terminal hyperlink to the web inbox filtered to match (`#/inbox`, `#/inbox?session=<lead>`, `#/inbox?project=<project>`). `I` or `:inbox` opens the link for the selection, or copies it when there is no display (over ssh).
- A lead (top-level session) that ends its turn with a question for the owner in its chat and filed no ask in that turn gets a "Waiting on you: <question>" item and a needs-you flag (reason `waiting`); a question or "waiting on you" it only quotes, or a waiting phrase that describes something ("Sessions waiting on you get a badge"), is not the session waiting; a question it also filed as an ask (in that turn or later) raises none, since the inbox has it. An older open ask does not hide a new question. It goes away when the owner engages with the session (types, messages it, reads its message), when the session files the ask or starts its next turn, or when it ends or is archived; a later turn that asks something new raises a new item, its own inbox conversation (owner report 2026-10-19: one item reused for days showed the whole history as one thread), while a turn that only repeats the request already raised (the same asking sentences, at least six words: "I'm still waiting on your yes to publish …") leaves the item as it is: not counted, not reopened, no push; a dismissed or handled one stays so until the session asks something new, and one withdrawn because the session moved on comes back without a push (owner report 2026-10-19: a coordinator's idle turns reopened one item 27 times). The owner can dismiss it anywhere: the web inbox lists it (and a session's own "needs you" flag) as a conversation whose reply goes to the session as chat and whose Archive dismisses it, `d` on the session in the TUI, `pyre attention dismiss <id>`. At most one phone push per lead per hour.
- A message from a session to the owner closes when he opens it in the web inbox, replies to it or acknowledges it (owner report 2026-10-19: items from long-finished sessions stayed open for ten days). Archiving its sender closes the ones he already read; an unread final report stays, since most archives are automatic. On the phone, "read" stays read.
- Mail that asks nothing of the owner is an **update**, never inbox mail (owner report 2026-10-19: "why are there a bunch of useless messages in my inbox", 144 unacked messages: 76 carriers of asks long decided, 65 status reports, digests and "ignore my previous message" corrections). The hub stores a session's message to the owner already acknowledged (`ack_ref` `pyre:update`) unless it needs him, read so that a doubt keeps it in the inbox: any question anywhere in it ("status?", "No rush, should I merge?"; softening never cancels one), a waiting phrase ("waiting on your go-ahead"), or a request, urgency or incident word ("please", "let me know", "I need the key", "review", "approve", "unless you object", "URGENT", "prod is down", "security", "blocked"; "nothing urgent" and "no action needed" are not); a "no reply needed" label outranks none of these. It also stays when it answers him (replies to his message, or he wrote to the session within a day and after its last message to him) or sets `request_ack`. Mail in mode `info` is classified the same way. An update raises no inbox item, flag or push and is not unacked mail on any surface (web, TUI, `pyre inbox`, Android, old clients included); it stays in the owner's mailbox, its session's and project's threads, the web inbox's Done box and search. The sender's delivery status says so ("stored as an update … for a decision use ask_owner"), and a question sent as a message is told that decisions go in `ask_owner`. The nightly cleanup report is an update unless part of the cleanup failed (the first, dry-run report is always for him).
- Mail leaves the inbox when it is done: an ask's carrier and the follow-ups in its thread are acknowledged when the ask closes in any way (answered, also in chat; defaulted; expired; withdrawn; dismissed; superseded), owner-approval asks included; the owner viewing a session's message (`pyre msg show`, the phone opening it) acknowledges that message; typing into the session or messaging it acknowledges its chat-like mail to him so far (sent without a thread and without `request_ack`; threads and acknowledgement requests wait until he opens them); marking a message item done (the phone's Done) acknowledges the mail it stands for; opening a message thread in the web inbox acknowledges it, so it moves to Done. `pyre inbox` as the owner lists only mail still waiting on him; `--all` lists the whole mailbox, updates marked `update`.

A message item's summary is an excerpt of the newest message (control characters and terminal escapes removed, at most 300 characters), so the list says what it is about. Phone pushes still carry only a generic title.

Delivery events are not all attention events. An agent sending ten progress messages should not generate ten urgent phone alerts. Avoid recursive loops where a notification acknowledgement becomes another notification.

The same pending approval can be visible on Android and the terminal. Once the native runtime resolves it, withdraw stale controls on all surfaces. Never invent which client won if the harness only reports that a request was resolved.

### Asks

A decision a session needs from the owner arrives as an **ask**, not as mail (decision I30): a one-line question, context written for someone who is not in the weeds (what, why it matters, what was tried, what each option does), 2–4 options, usually a default, and a deadline. The deadline is an hour unless the asker sets one; one that would fall at night moves to about 08:00 Pacific unless the ask is urgent. At the deadline the default is applied (state `defaulted`), or the ask expires without one; irreversible actions carry no default. The asking session hears the outcome as a reply to the ask's message and keeps working on the default path meanwhile.

Each ask is one inbox item (attention kind `ask`): read, done and snooze work as for other items, answering is one keypress per option, and several asks can be answered together and sent once (`pyre ask answer ask_A b ask_B a`). From the terminal: `pyre ask ls [--open] [--project]`, `pyre ask show <id>`, `pyre ask answer`, `pyre ask dismiss`, `pyre ask withdraw`; `--json` on all of them.

Answering in chat (owner request 2026-10-19: "asks don't seem to go ahead when I respond in chat"). One rule: **writing to the session itself answers its open asks; a reply in a thread does not.** Anything the owner types into the session (TUI or web terminal, a local tmux attach) to start a new turn after the turn that asked, and a Pyre message from him to the session that is not a reply in a thread (`pyre send`, the TUI composer `m`, the web inbox's reply to a "waiting on you" item), answers the session's open asks: state `answered`, `answer.source` `chat`, `answer.text` his words, `answer.with` the other asks the same words answered. The default can no longer fire and the inbox items close; the session already has his words, so its decision notice is stored in its inbox without starting a turn. A reply in an ask's thread in the web inbox ("what do you think is better?") is only a message to the session: it can answer, withdraw or ask again. To make the text the answer, use **Answer with this** in the web composer, or `pyre ask answer <id> --text "…"`. Proposals (approve/reject a standing grant or fact), owner-approval requests and asks with a held answer are never answered in chat. What counts as typed is strict, so nothing typed before he saw the question answers it: only the prompt that starts a later turn than the one that filed the ask, after the session sat idle for at least 5 seconds (a prompt typed while the session was busy is queued by Claude and starts the next turn at once: it is not an answer), not in the first turn of a run (launch, resume, handoff), and only a prompt a person typed (not a Pyre message, a plugin's message, a task notification, `/compact`, or Pyre's own prompts). Typed answers are read from the transcript a few seconds after the turn starts.

Dismissing: an open ask can be archived only by dismissing it: the web inbox's Dismiss (it asks to confirm; bulk "archive older" never dismisses), `d` on the session in the TUI (confirms), `pyre ask dismiss <id>` or `pyre attention dismiss <its item>`. A dismissed ask is withdrawn by the owner with no option; its default never applies, and the session is told ("withdrawn by the owner (dismissed by the owner: …)").

Several like decisions ("merge these 5 reviewed PRs") come as one batched ask with items: the web inbox shows each item with its own option buttons plus "Apply to all" and sends them together; from the terminal `pyre ask answer <id> [<option for the rest>] --item pr-12=merge --item pr-13=hold`. A lasting go-ahead ("merge PRs once reviewed and green") is a standing grant, and only the owner creates one: a session proposes it (`propose_grant` / `pyre propose grant --action merge --option merge --why "…"`), which is an ordinary ask "Remember this go-ahead? merge → merge" with Approve / Reject and no default. When he approves, Pyre records the grant with his own answer text (if he typed any) and the ask ID; nothing the session wrote becomes his words. The owner can also add one himself (`pyre grant add --action merge --option merge [--note …] [--expires 7]`). A grant holds for the project or for a session's tree (children inherit it, never broaden it) and expires after 7 days by default (30 at most). A later ask is answered at once only when it names exactly that action, offers that option, has a default and is not irreversible, and its topic was not decided in the last 7 days or reopened; production deploys, deleting data, spending money, force-pushes, public releases and account changes are never covered. Each grant has an informational inbox item ("Standing go-ahead: merge → merge") that collects every ask it answered, and the inbox shows those asks as "Answered by a standing grant". The project page in the web app (Standing go-aheads) and the TUI project's Grants tab (`x`) list and revoke them; so do `pyre grant ls [--all]` and `pyre grant revoke <id>`.

Rules Pyre enforces so the inbox stays small:

- **One item per topic.** Every ask has a topic key. Asking again on an open topic merges into the existing item (its count and updates grow; no new notification). Asking on a decided topic returns the decision instead of asking again; an agent re-asks only with `reopen` and a reason. A similar open ask under another topic comes back to the agent as a possible duplicate.
- **Only top-level sessions reach the owner.** A session started by another session asks its parent instead; the hub forwards the ask there.
- **Record keeping for agents.** `find_asks` (topic key or full text, open asks plus those decided in the last seven days) lets an agent check whether a question was already asked or answered before it asks or messages. A correction is a merge on the same topic or `withdraw_ask`, never a second message.

Agent guidance (the session guide, `pyre guide`) says the same in a few lines: decisions through `ask_owner` with context the owner can decide from alone (the hub rejects a new ask under 300 characters or with an option lacking a detail), `find_asks` first, clarification requests answered with `reply_to` and self-contained, peers messaged only when they must act, no progress pings, final results once; a project's lead keeps the project page (the owner's main view of the project in the web app) current at milestones.

Automatic reports from a child session to its parent are kept quiet too: none when the child messaged its parent in the five minutes before that turn ended (an earlier mid-turn question does not count), one report for a turn that finishes and then ends, a first line of the form "<title> finished: <first sentence>" with at most 400 characters of the last message, and reports for a parent without a live run wait for its next run.

## Agent slash commands

Every Claude session Pyre starts gets seven slash commands for requests the owner otherwise retypes (2026-10-13, from his last 1000 messages): `/kickoff [what to build]`, `/open-items`, `/ship [PR or branch]`, `/brief`, `/deliver [what]`, `/cleanup` and `/pair [question]`. They are Claude Code skills embedded in the binary from `internal/runtime/claudeplugin/skills/`, which Pyre writes into the session's Claude config dir before each launch (`<CLAUDE_CONFIG_DIR or ~/.claude>/skills/<name>/SKILL.md`, the per-account profile when there is one): personal skills run by bare name, while plugin skills would need `/pyre-session:<name>` (Claude Code 2.1.296). Each dir Pyre writes is marked Pyre-managed (`.pyre-managed`: Pyre version and content hash) and rewritten only when its text changes; a same-named skill without that marker is the owner's own and wins, and Pyre leaves it untouched (logged once). Pyre deletes nothing else there. Each command is a short, firm procedure built on his standing preferences: verdict first and short, parallel children, bias to action, Pacific times, PR reports with URL, pushed, CI state and a one-line risk note, reports as self-contained HTML in `~/Downloads` opened with `xdg-open`/`open`.

The reference comes from the skills' frontmatter, so it cannot drift: `pyre commands` (`--json`; `pyre commands <name>` prints the full procedure) and the "Agent commands" section of the TUI help (`?`). Codex sessions do not get the skills; the agent guide points them at `pyre commands <name>` to follow the same procedure.

## Android companion

Begin with HAPI's Kotlin/Compose client if the backend gate passes. Deliver a signed APK for sideloading with repeatable build instructions and an update route using the same signing identity.

Primary mobile capabilities:

1. See sessions and attention requests across the fleet.
2. Read/reply, answer structured questions, approve supported requests, interrupt, and start a session on an online machine.
3. Open project briefs, documentation, and published artifacts; comment and share feedback.
4. Receive useful background notifications while the screen is off, with reply/approval actions when supported.
5. View machine and account health and understand why work paused.

The first full-terminal path can open the existing authenticated web terminal. It is an explicit fallback until native terminal support is implemented, not a promised built-in Android terminal. The app may cache project material and drafts; queued offline actions must show pending status and reconcile after reconnect.

Native push is a separate dependency from session networking. A private Firebase-enabled build requires matching app/hub configuration. Do not claim push works simply because a debug APK can connect in the foreground. Verify on the user's actual Android setup, including network reachability through Twingate.

## Management views

**Machines:** online status, last seen, agent availability, versions, environment health, resource use, update/restart outcomes, and a direct SSH action where configured.

**Accounts:** provider, friendly name, health, usage/reset timestamps, active assignments, and fallback eligibility. Never display tokens. Clearly distinguish subscription usage from API billing.

The TUI header shows fleet-wide subscription utilization per provider, from the accounts and nodes data it already loads: `claude 5h 47%~ · wk 64% (4/5) !1   codex wk 30%   agy 5h 8% · wk 62%`. Each number is the mean used percent of that window over the provider's enabled accounts, each account weighted equally (Pyre has no per-account capacity; for accounts on one plan the mean is the used share of the pooled cap). The 5-hour mean takes readings up to 15 minutes old; the weekly mean also takes a good reading up to 3 hours old, since an account idle in Pyre is re-read only when chosen and its week moves slowly (a failed probe's carried-over numbers never count). Accounts left out of both (unknown, re-auth, not yet observed, older readings) show as `(n/m)`, or `~` when abbreviated; a `~` after the 5-hour number says fewer accounts have a fresh 5-hour reading than the week. `!N` counts accounts at their limit (amber; red, with `none ready`, when no account is available). A window whose reset has passed counts as 0%. The weekly number is the all-models week (model-scoped weeks are in the Accounts view). A provider without a 5-hour window (Codex plans that report only the week) shows only `wk`. `—` means not reported. agy has no Pyre-managed logins, so each machine's own agy login counts as one account (one per Google identity). Where agy (1.1.11 or later) is installed, signed in and was used in the last 7 days, the node observer runs `agy -p "/usage" --output-format json` (no agent turn, no quota spent) in the background at most every 5 minutes: in a scratch directory with its log there (`--log-file`, so agy's `cli.log` and `log/` are untouched), a minimal environment without API keys or auth overrides, its own process group killed on a 20 s timeout. It keeps only the parsed percentages and resets, tied to the signed-in identity, and reports them in the harness inventory (`HarnessInfo.Usage`). A reply that shows a turn or a conversation disables the read for that agy version. agy has separate buckets per model group (Gemini, Claude and GPT, Argon), and the group a session draws on depends on its model and, for Argon, on the plan, so each agy window is the most used bucket across groups; once that bucket resets the window reads 0% until the next read, even if another group's bucket is still used. Each agy start may run agy's background auto-updater (agy 1.4.2 has no switch for it), which is why only machines that use agy are read. Each read makes a few Google calls and starts agy (a few seconds), and every machine on one Google login reads it separately. The Accounts view shows the reading on the own-login line. Narrow terminals drop the 5-hour window, then abbreviate (`cl 64%~!1   cx 30%   agy 62%`), before the filter tag, then drop the segment. Clicking it opens Accounts.

**Connections:** service/account, verified status, machine availability, project/environment references, and the action required to make it usable on another node.

**Environments:** skills, plugins, tool versions, configuration layers, and pending drift. Show a concrete change preview when adopting or applying configuration; preserve personal changes.

## Design validation

Test keyboard-only navigation, narrow terminals, long session names, offline nodes, bursts of updates, search, and reconnect without selection loss. On Android test small screens, screen-off notifications, resumed drafts, artifact download/open, and stale approval removal. Capture screenshots/recordings of these flows using synthetic data for review.
