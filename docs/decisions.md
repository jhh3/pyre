# Decisions and assumptions

This register separates user requirements from recommended technical choices. Implementation agents should resolve routine technical choices themselves and record evidence. Do not repeatedly ask the user to restate decisions already made.

## Confirmed user direction

| Decision | Consequence |
| --- | --- |
| Mac and Linux machines; SSH and Twingate already used | Reuse that network and access model. Do not require a replacement mesh VPN. |
| New sessions through a shared launcher are acceptable | Managed lifecycle can be the first supported path. |
| Terminal-first, polished management interface | Preserve native Claude/Codex interaction while adding fleet and project views. |
| Agent Deck was rejected | It is not the recommended product or UX foundation. |
| Diverse orchestration styles | Enable manual dispatch, supervised work, and agent-directed delegation with the same primitives. |
| Projects may have some structure but must remain optional | Provide shared briefs/docs/artifacts without forcing all sessions into projects. |
| Same-provider subscription fallback; notify when exhausted | No implicit cross-provider fallback. |
| Hive, Outfit, and Rota can be changed or rewritten where useful | Preserve data and behavior during incremental migration; rewrite scope follows evidence. |
| Daemons are acceptable; modest infrastructure is acceptable | Resource-bounded node services and a small hub are reasonable. |
| Android and willingness to build/sideload | Deliver an installable Android client, not only a mobile mockup. |
| Research precedents and avoid needless reinvention | Validate HAPI, native harness protocols, and messaging patterns before rebuilding them. |
| Private personal GitHub repository and a parallel Opus implementation handoff | Keep this repository private; supply bounded work packages, ownership, contracts, and acceptance. |

## Recommended defaults subject to technical validation

| ID | Default | Why | Revisit when |
| --- | --- | --- | --- |
| D01 | One always-on hub plus execution-node services | Central shared content and durable routing simplify mobile access and reduce all-to-all networking. | Availability/network tests show a better placement. |
| D02 | Existing host first; VPS optional | Minimal new infrastructure. server is a pilot candidate, not an irrevocable production choice. | The owner needs independent availability or easier ingress. |
| D03 | HAPI behind a backend interface | Existing session and mobile plumbing may save substantial work. | Native handoff, identity, account profiles, licensing, or recovery fails G0 evaluation. |
| D04 | Go CLI/TUI and personal service facade; TypeScript backend adapter as needed; Kotlin/Compose Android reuse | Fits Outfit's implementation and HAPI's existing runtime/client. | A spike establishes that another packaging boundary materially reduces duplication. |
| D05 | SQLite metadata and ordinary file storage on the hub; local node caches/outboxes | Small installation, transactional local state, simple backups. | Actual capacity/availability requirements justify a broker or external storage. |
| D06 | No separate message broker at launch | Reuse backend persistence and explicit message semantics first. | A proven transport limitation requires one; NATS is a researched option. |
| D07 | Versioned shared documents and immutable artifacts, locally cached | Portable review, offline reading, and clear concurrent-edit behavior. | User feedback establishes a better authoring workflow. |
| D08 | Retain Hive's local indexes and existing sync during early integration | Avoid a memory rewrite blocking first value. | Measured freshness or sync failures justify changing the transport. |
| D09 | Per-session account runtime and fleet-visible account health | Prevent concurrent sessions from changing each other's identities. | Harness validation determines the exact supported home/keychain/auth mechanism. |
| D10 | FCM for initial Android background push | Fits the existing Android client's implementation. | The device lacks Play services or user prefers another delivery provider. |

These defaults are a proposal. User approval of the planning exercise is not proof that a backend works or authorization to mutate every existing machine's configuration.

## Questions for experiments rather than another user questionnaire

1. Does HAPI preserve the native Claude/Codex experience through remote interaction, attachment, disconnect, and resume on the actual versions installed?
2. Can the runner launch sessions with distinct verified account/environment profiles without affecting another session or the user's default login?
3. How does each harness handle authentication refresh and cross-account resume? Which operations require a restart, and which history/config items must remain stable?
4. Can the backend's message persistence be extended into a single trustworthy inbox with stable sender/reply identity and uncertain-outcome handling?
5. Which native subagent events and controls are actually exposed? Preserve native behavior even where the fleet UI cannot expose every child operation.
6. Can Android reliably reach the chosen HTTPS hub through the existing network while background push still works under screen-off conditions?
7. What resource envelope keeps server and the Mac responsive under their real workloads?
8. Which checked-out Hive/Outfit/Rota revisions and local changes represent the owner's current intended behavior?

## Decisions requiring user preference eventually

The exact production hub host, credential sharing scope across personal/work machines, notification preferences, and visual direction remain configurable choices. Use isolated development defaults meanwhile; do not make the user answer these before proving core behavior. Present a concrete migration/configuration proposal before applying it to active personal environments.

## How to amend decisions

Record the decision, evidence, compatibility impact, and changed requirements/contracts. Preserve confirmed product behavior. The lead may change a technical default without a ceremony when evidence supports it, but must notify affected workers and update fixtures, ownership, and acceptance expectations together.
